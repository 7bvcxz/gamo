# Motorio: One Shot — 테스트 목록

무엇이 어떤 결함을 막고 있는지, 그리고 어떻게 돌리는지. 사용자가 이름을 부르면
해당 항목만 수행한다.

전부 돌리기:

```
cd motorio-oneshot
for t in tests/test_*.gd; do godot --headless --path . --script res://$t; done
```

하나만 돌리기:

```
godot --headless --path . --script res://tests/test_touch.gd
```

> **종료 코드로 판단하지 않는다.** Godot headless는 스크립트 오류에도 0을 반환할 수 있다.
> 출력의 `PASS`/`FAIL`과 `SCRIPT ERROR`를 함께 본다. 결과 없이 멈추면 타임아웃을 늘리지
> 말고 `timeout -s KILL`로 로그를 파일에 받아 마지막 `SCRIPT ERROR`부터 읽는다.

## 브라우저 테스트 (사람이 부를 때)

headless는 파싱과 논리만 본다. 아래는 렌더링·입력·배포가 실제로 도는지 보는 것이고,
이름을 부르면 수행한다.

### `real test` — 표준 시나리오

**근처 수정 광맥에 채굴기 2대를 *위를 보게* 놓고, 각 채굴기에 고양이 1마리, 배치 안 한
고양이 1마리 (고양이 총 3마리).** 이 상태로 1배속으로 **3일차 밤까지** 돌린다. 1분마다
스크린샷을 찍고, 몇 분에 한 번씩 Grim에게 할 일을 시킨다.

방향이 시나리오의 일부다. 채굴기는 바라보는 칸으로 뱉으므로 나란한 광맥에 **동쪽을 보게**
놓으면 둘 다 막힌다 — 왼쪽은 오른쪽 채굴기로, 오른쪽은 세 번째 광맥으로. 위를 보게 놓으면
빈 바닥에 떨어뜨리고 유휴 고양이가 그것을 기지로 나른다. 그게 실제로 생산되는 배치다.

Grim에게 시키는 것(순환): 손 채굴 · 계기 열기 · 가챠 1연차 · 건설 목록 · 남쪽 산책 ·
화면 축소/확대. **작업 중인 고양이를 들거나 X를 누르지 않는다** — 들면 그 채굴기가 서고
X는 기계를 해체하므로, 관찰하려는 배치가 사라진다.

배치는 **`F4`(`debug_scenario`) 한 번**으로 만든다. 손으로 만들면 "왼쪽으로 1250ms 걷고
Z, 오른쪽으로 850ms 걷고 위를 보고 Z" 같은 타이밍 홀드가 열두 번이고, 한 번만 어긋나면
고양이가 채굴기가 아니라 옆 광맥 위에 선다. 그 회차는 아무것도 생산하지 않는데 그 모습이
**게임 버그와 똑같이 보인다** — 실제로 첫 파일럿이 그렇게 됐다. 검사 도구가 버그처럼
실패하는 것이 제일 나쁘다.

확인하는 것:

- 두 채굴기가 모두 돌고 수정조각이 실제로 나오는가
- 배치된 고양이 2마리가 각자의 채굴기에 서 있는가, 작업 애니메이션이 나오는가
- 남은 1마리가 유휴 행동(바닥의 자원을 기지로 나르기)을 하는가
- 세 마리가 서로의 그림자·허기 막대를 덮지 않는가
- 허기가 떨어지면 밥통으로 가고 돌아오는가
- 밤에 셋 다 숙소로 들어가고 아침에 자기 자리로 돌아가는가
- HUD의 수정 수치가 실제 산출과 맞는가
- Grim의 행동이 배치를 방해하지 않고 각각 의도한 화면을 여는가

> **정산 카드는 `Enter`로 넘기지 않는다.** `Enter`는 `build` 액션에도 묶여 있어서 플레이
> 중에 누르면 설치를 시도한다. 카드는 화면 가운데 상자의 어두운 픽셀 비율(카드 0.96 대
> 플레이·밤·새벽 0.04 이하)로 감지하고 `Space`로 넘긴다.

### 그 밖의 브라우저 검사

| 이름 | 하는 일 |
|---|---|
| `play test` | 1배속으로 3번째 밤까지, 1분마다 스크린샷. 회차 수를 지정할 수 있다 |
| `mobile test` | 390×844 뷰포트에 실제 터치 이벤트. **`mouse.click()`은 쓰지 않는다 — 터치 레이어가 합성 마우스 이벤트를 소비한다.** 그리고 **누르고 있는 입력을 반드시 포함한다** — 아래 참고 |
| `deep test` | 랜덤 플레이가 닿지 않는 화면: 건설 목록, 계기, 가챠 10연차, 줌 양방향 한계, 설정 |
| `night test` | 밤 연출 전체를 0.7초 간격으로 촬영 |
| `perf test` | 프레임률. **같은 빌드를 3회 이상 재고 중앙값으로 판단한다** |
| `deploy test` | 배포된 URL을 열어 기대한 해시 PCK가 로드되고 캔버스에 색이 두 가지 이상 그려지는지 |

> **모바일 검사는 탭만으로 끝내지 않는다.** 채굴은 누르고 있는 동작이고, 패드가 누름만
> 보내던 시절 폰에서는 캘 수가 없었는데 **탭만 확인하는 검사로는 영원히 안 보인다.**
> `touchscreen.tap()`은 홀드를 표현할 수 없으므로 CDP로 직접 보낸다:
>
> ```js
> const cdp = await page.context().newCDPSession(page);
> const touch = (type, x, y) => cdp.send('Input.dispatchTouchEvent', {
>   type, touchPoints: type === 'touchEnd' ? [] : [{ x, y, id: 1 }] });
> await touch('touchStart', x, y); await sleep(13000); await touch('touchEnd', x, y);
> ```
>
> **"터치가 빗나갔다"와 "게임이 틀렸다"를 먼저 가른다.** 채굴 검증이 네 번 실패했는데
> 전부 조작이 엉뚱한 칸에 선 것이었고, 매번 게임이 고장난 것과 똑같이 보였다. 패드는
> 눌린 버튼을 다르게 그리므로, 두 프레임의 패드 영역을 비교해 **버튼에 불이 들어왔는지**를
> 먼저 본다. 안 들어왔으면 좌표 문제이고, 게임에 대해서는 아직 아무것도 알아낸 게 없다.

> **혼잡한 화면에서 픽셀로 재려 하지 않는다.** 고양이 여덟 마리가 있는 기지에서 게이지 아래
> 그림자를 픽셀로 찾으면 옆 고양이·드릴·기계의 어두운 부분에 붙어 편차 52px 같은 노이즈가
> 나온다. 같은 질문을 `test_crowd`가 정확히 답한다 — 화면은 그것이 이상해 *보이는지*를,
> 테스트는 그것이 실제로 어긋나는지를 본다.

브라우저 검사 준비물은 `AGENTS.md`의 "실수와 교훈"과
`~/.claude` 메모리의 browser-test-setup에 있다. 요약: Playwright를 스크래치패드에
설치하고 `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`로 띄운다.
**준비 완료 판정은 "캔버스가 있다"가 아니라 "캔버스에 색이 두 가지 이상 그려졌다"이다.**

## 이 목록에 항목을 더할 때

테스트는 **인스턴스가 아니라 결함의 종류**를 잡아야 한다. 지금까지 실제로 나온 종류:

1. 화면이 말하는 키가 다른 일을 한다 (`test_hints`)
2. 터치가 키보드와 다른 상태에 도달한다 (`test_touch`)
3. 고정한 한국어 조사가 단어와 안 맞는다 (`test_hints`)
4. 절차적 배치가 규칙적으로 반복된다 — 다양성 지표는 주기성을 못 본다 (`test_ground`)
5. 상태를 읽는 코드가 상태 기계보다 먼저 돈다 (`test_night`)
6. 셋업 헬퍼가 검사하려는 문제를 미리 해결해 준다 (`test_belt`의 주석)

**새 검사를 넣으면 고치기 전 코드에서 실패하는지 반드시 확인한다.** 양쪽에서 통과하는
검사는 아무것도 증명하지 않는다.

그리고 **왜** 통과했는지도 확인한다. `test_walk`의 중앙 검사는 두 번 공허하게 통과했다 —
한 번은 하루가 끝난 뒤에 봐서 작업 중인 고양이가 하나도 없었고, 한 번은 `place_cat`이
이미 정확히 놓아서 걸어오는 경로가 실행되지 않았다. 검사가 보려는 상황이 실행에 실제로
포함됐는지를 함께 assert한다(`worked > 1000`, `hauled_from_east`).
