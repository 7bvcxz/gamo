# 눈 위 바위 타일셋 — 생성 사양서

`tile_rock_47.png`를 다시 만들기 위한 사양이다. 그대로 복사해서 생성 모델에 넘기면 된다.

앞선 시트가 왜 쓸 수 없었는지, 무엇을 대신 요구해야 하는지, 받은 뒤 무엇을 확인해야
하는지가 순서대로 들어 있다. `build_rock.py --audit`이 여기 적힌 검사를 그대로 수행한다.

---

## 1. 지난 시트에서 실제로 무엇이 잘못됐나

받은 47장을 측정한 결과다. 인상이 아니라 숫자다.

| 확인한 것 | blob47이 요구하는 값 | 실제 |
|---|---|---|
| 돌이 **어느 변에도 닿지 않는** 타일 수 | 1장 (mask 0, 고립된 바위) | **12장** |
| 16가지 "돌이 닿는 변" 조합 | 16가지 모두 | **12가지** (`E`·`NW`·`EW`·`SW` 없음) |
| 서로 다른 8방향 연결 경우 | 47가지 | **약 15가지** (나머지는 같은 모양의 변형) |
| 인덱스 46 = mask 255 (사방이 돌인 내부) | 칸 전체가 돌 | 돌 비율 **15%** |
| 인덱스 0 = mask 0 (눈 한가운데 고립된 바위) | 가운데 돌 하나 | 돌 비율 **0%** (순수 눈) |

즉 47칸을 그리기는 했지만 **연결 경우를 47가지로 나누지 않았다.** 가장자리 몇 종에
변형을 여러 장 붙이고, 순수한 눈 3장과 자갈 장식을 채워 47을 맞췄다.

여기에 더해 타일링을 불가능하게 만드는 형식 문제가 둘 있었다.

- 이미지 바깥에 **크림색 페이지 여백**이 있었다(좌 14px, 상 15px). 그래서 8×6으로
  나누면 모든 표본이 어긋난다.
- 각 칸이 **둥근 모서리와 밝은 테두리를 가진 카드**로 그려졌다. 붙이면 칸마다 흰 선이
  생겨 눈밭이 아니라 욕실 바닥이 된다.

## 2. 권장: 47장이 아니라 **모서리 조각 20장**을 요구한다

47장을 한 이미지 안에서 서로 아귀가 맞게 그리는 것은 생성 모델이 실패한 바로 그
작업이다. 훨씬 쉽고 결과가 수학적으로 보장되는 요구 방법이 있다.

한 타일을 2×2 사분면으로 나누면, 각 사분면의 그림은 **인접한 두 변과 그 사이 대각선**
세 개로만 정해진다. 경우의 수는 다섯 가지뿐이다.

1. `INNER` — 두 변 모두 돌, 대각선도 돌 → 사분면 전체가 돌
2. `NOTCH` — 두 변 모두 돌, 대각선만 눈 → 바깥 모서리에서 눈이 둥글게 파고듦
3. `VERT` — 한 변만 돌 → 경계가 세로로 지나감
4. `HORZ` — 다른 한 변만 돌 → 경계가 가로로 지나감
5. `OUTER` — 두 변 모두 눈 → 안쪽 구석에만 돌이 둥글게 남음

이 다섯을 네 방향으로 그리면 **20장**이고, 그걸로 47가지를 전부 조립할 수 있다.
조립은 이쪽에서 코드로 한다. 사분면이 항상 같은 위치에서 만나므로 이음매가 어긋날
수가 없다.

> **요구할 것**: 타일 한 변의 절반 크기(예: 64×64) 조각 20장, 5행 × 4열.
> 행은 위에서부터 `INNER` · `NOTCH` · `VERT` · `HORZ` · `OUTER`,
> 열은 왼쪽부터 좌상 · 우상 · 우하 · 좌하 방향.

대가는 하나다. 돌 무늬가 반 타일 주기로 반복될 수 있다. 그건 이쪽에서 칸마다 미세한
변화를 섞어 깨뜨릴 수 있으므로, 이음매가 어긋나는 것보다 훨씬 나은 문제다.

## 3. 그래도 47장으로 받겠다면

### 3.1 형식 (하나라도 어기면 쓸 수 없다)

- 캔버스 **1024 × 768**, 타일 **128 × 128**, **8열 × 6행**. 8과 6으로 정확히 나누어
  떨어져야 한다.
- **여백 없음.** 이미지 가장자리에서 바로 첫 타일이 시작한다.
- **칸 사이 간격 없음.** 타일끼리 맞닿는다.
- 칸마다 **테두리·둥근 모서리·그림자·액자 금지.** 타일은 카드가 아니라 지면의 일부다.
- 칸마다 **자체 조명 그라데이션 금지.** 가운데가 밝고 가장자리가 어두우면 붙였을 때
  칸이 눈에 보인다. 빛은 시트 전체에서 한 방향으로 균일하게.
- 마지막 칸(6행 8열, 인덱스 47)은 **비워 둔다.**
- 배경 투명도 없이 불투명 PNG.

### 3.2 이음매 규칙 (이게 전부다)

돌 영역이 칸 경계를 어떻게 지나는지가 유일하게 중요한 것이다.

- 이웃이 **돌인 변**: 그 변의 **가운데 60%를 돌이 빠짐없이 덮어야 한다.** 변에 닿기만
  하는 게 아니라 덮어야 한다.
- 이웃이 **눈인 변**: 돌이 그 변에서 **타일 크기의 10% 이상 떨어져 있어야 한다.**
  스치기만 해도 옆 눈 칸으로 돌이 새어 나온 것처럼 보인다.
- 경계선은 항상 **변의 한가운데를 수직으로** 지난다. 왼쪽으로 치우친 타일과 오른쪽으로
  치우친 타일을 붙이면 단차가 생긴다.
- 눈이 돌 위로 얹힌 **흰 테두리(눈처마)의 두께가 모든 타일에서 같아야 한다.**
- **모서리 눈**: 두 변이 모두 돌인데 그 사이 대각선이 눈일 때만, 그 모서리에서 눈이
  둥글게 파고든다. 파고드는 깊이는 타일의 **30%를 넘지 않는다.**

### 3.3 그림

- 돌은 회색 자갈이 뭉친 질감, 눈은 밝고 살짝 푸른 톤. 같은 프로젝트의 눈 바닥
  타일과 같은 화풍.
- 돌 위에 눈이 조금 얹힌 느낌은 좋지만, **눈 얼룩을 타일 안쪽에 크게 넣지 않는다.**
  안쪽은 이웃과 무관하게 늘 같아야 하는 부분이다.
- 자갈·풀·발자국 같은 **장식을 넣지 않는다.** 47칸은 전부 연결 경우에 쓰인다.
  장식 변형은 별도 시트로 받는다.

### 3.4 47칸의 내용

인덱스는 row-major(`index = row × 8 + column`), 좌표는 아래와 같다.

```
NW   N   NE
 W  [X]   E
SW   S   SE
```

비트: `N=1  E=2  S=4  W=8  NE=16  SE=32  SW=64  NW=128`

대각선은 인접한 두 직교 방향이 모두 돌일 때만 유효하다
(`NE = NE && N && E`, 나머지도 같은 규칙).

mask는 **주변 칸에 돌이 있는지**를 뜻한다. 현재 칸은 언제나 돌이다.

## 4. 받은 뒤 확인 (`build_rock.py --audit`)

1. 이미지 크기가 정확히 1024×768이고, 가장자리에 여백이 없는가
2. 돌이 어느 변에도 닿지 않는 타일이 **정확히 1장**(인덱스 0)인가
3. "돌이 닿는 변" 조합 **16가지가 모두** 나타나는가
4. 인덱스 46이 거의 100% 돌, 인덱스 0이 20% 안팎의 돌인가
5. 각 타일의 실제 변 접촉이 위 표의 mask와 일치하는가 — 어긋나는 장수가 몇인가

5번이 0이면 그대로 쓴다. 지난 시트는 40장이 어긋났다.
