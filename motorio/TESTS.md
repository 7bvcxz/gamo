# Motorio — 테스트 목록

무엇이 어떤 결함을 막고 있는지, 그리고 어떻게 돌리는지. 사용자가 이름을 부르면
해당 항목만 수행한다.

전부 돌리기:

```
cd motorio
for t in tests/test_*.gd; do godot --headless --path . --script res://$t; done
```

하나만 돌리기:

```
godot --headless --path . --script res://tests/test_touch.gd
```

> **종료 코드로 판단하지 않는다.** Godot headless는 스크립트 오류에도 0을 반환할 수 있다.
> 출력의 `PASS`/`FAIL`과 `SCRIPT ERROR`를 함께 본다. 결과 없이 멈추면 타임아웃을 늘리지
> 말고 `timeout -s KILL`로 로그를 파일에 받아 마지막 `SCRIPT ERROR`부터 읽는다.

## 자동 테스트 (headless, 37개)

### 규칙과 진행

| 테스트 | 지키는 것 |
|---|---|
| `test_sim` | 아이템 흐름, 기계 tick, 자원 집계 |
| `test_progression` | 해금 순서, 광맥 순도, 온기 반경 |
| `test_flow` | 벨트·분배기·교환기를 지나는 자원의 경로 |
| `test_belt` | 벨트 속도와 등급. **셋업 헬퍼가 발전기를 켜두면 전력 없는 경로가 한 번도 실행되지 않는다** |
| `test_belt_art` | 벨트가 이웃을 보고 직선/코너를 고르는 규칙과 회전 방향, 타일 크기와 이음매. 그리는 모양이 저장된 값이 아니라 이웃에서 나오므로, 이웃이 바뀔 때 갱신을 잊을 자리가 없다 |
| `test_build` | 설치·회수 규칙, 광맥 위 제약 |
| `test_meter` | 처리량 측정 창과 설계 수치 |
| `test_workers` | 고양이 배치, 허기, 작업 속도. **떨어진 자원은 가장 가까운 노는 고양이 하나만 맡는가**, 노는 고양이가 실제로 어슬렁거리며 숙소 근처를 벗어나지 않는가 |
| `test_opening` | 추락 지점의 첫 13분. **기지를 바라보고 Z로 연료가 들어가는가**(손으로 캔 열석은 여기 말고 불에 닿을 길이 없었다), 자재는 남는가, 세 번째 임무가 온기를 정확히 9칸으로 만들고 **그 순간 얼어붙은 고양이가 온기 안에 들어오는가**. 기지도 거처도 없는 세계로 시작하는가, **오프닝 동안 하루가 멈추는가**, 상자에서 두 번 나오고 세 번째는 없는가, 기지가 추락 지점 2칸 안에만 놓이고 **놓는 순간 세계의 중심이 그리로 옮겨가는가**(옮겨간 좌표가 저장되지 않으면 불러온 세계의 안개·숙소·광맥 고리가 화면의 불과 다른 자리에 온다), 체온 0이 오프닝을 끝내지 못하는가. 임무는 번호를 직접 올리지 않고 **세계를 바꾼 뒤 임무가 무엇이 됐는지 묻는다** |
| `test_frozen` | 구조 전체. 시드 200개에서 시작 반경 안에 얼어붙은 고양이가 **항상** 있는가(상자 3개가 1마리로 줄면서 한 번의 충돌이 곧 시작 불가가 된다), 안으면 정확히 절반 속도이고 달리기가 막히는가, 기지 2칸 밖에서는 녹지 않는가, 놓아둔 그 자리에서 깨어나는가. **속도는 상수를 되읽지 않고 실제로 걸려서 잰다** |
| `test_carry` | 고양이를 안고 옮기기. 들린 고양이는 시뮬레이션하지 않는다 |
| `test_walk` | **하루 동안 고양이가 순간이동하지 않는가.** 1초 간격과 매 틱 두 가지로 재고, 작업 중인 고양이가 채굴기 정중앙에 서는지 확인한다. 오른쪽에서 기지로 나르는 경로를 실제로 만들어 넣는다 |
| `test_crowd` | **고양이 8마리를 하루보다 길게 실제로 돌리며 매 틱 게이지·몸·그림자 간격을 잰다.** 걷고 먹고 귀가하는 구간이 실제로 포함됐는지도 함께 확인한다 |
| `test_gacha` | 확률표 합계, 경계값, 2만 회 분포, 코인 차감, 등급별 작업 배율, 세이브 왕복 |

| `test_base_menu` | 기지 창의 줄이 전부 같은 방향으로 읽히는가. 하는 일은 제목 아래, 드는 비용은 오른쪽. 연료 줄만 거꾸로였다 |
| `test_title` | 시작 화면. 그림이 **모든 화면비에서 화면을 덮는가**(16:9에서 덮는 배율은 화면과 정확히 같은 크기라 조금만 어긋나도 뒤가 드러난다), 비율이 늘어나지 않는가, 메뉴가 그림 위에 얹히는가. 그리고 시작 메뉴. 세이브가 없으면 이어하기가 **없는가**(있는데 거절하는 줄은 건너뛰는 법을 가르친다), 커서가 감기는가, 각 줄이 실제로 하는 일, `처음부터`가 세이브를 지우는가(안 지우면 다음 실행이 이미 버린 게임을 이어하겠다고 한다), 그리고 그리는 자리와 누르는 자리가 같은가 |
| `test_ambience` | 실내에서 추위 소리가 멎는가. 침대는 체온만 읽고 있었고 그녀는 하루 중 가장 낮은 체온으로 숙소에 들어오므로, **마침내 안전해진 그 순간에 추위가 가장 컸다.** 잠자리 연출 전체(고양이들이 아직 걸어오는 GATHER 포함)에서 조용한지, 나가면 다시 들리는지 |

| `test_cat_art` | 월드 레이어가 땅 위에 그리는 판단들. 사료 상자가 없으면 개수도 안 그리는가(상자는 0.20.74에 시작 배치에서 빠졌는데 숫자만 남아 눈밭에 `200`이 떠 있었다), **도구는 기계의 것인가** — 맨 광맥의 고양이는 앞발로 파고 채굴기의 고양이는 기계를 돌리는데 둘 다 `CAT_WORKING`이라 그리는 쪽이 상태만 묻자 없는 드릴을 들려 줬다, 작업 중인 고양이의 **발이** 칸 한가운데를 딛는가(고양이 위치는 몸통이고 발은 10px 아래라 칸 중앙에 놓으면 타일의 1/3만큼 남쪽에 선다), 키트 세 장이 실재하고 든 것과 놓인 것이 다른가 |
| `test_filter` | 캐릭터 아트의 샘플링. 어떤 배율에서도 소스 픽셀이 화면 픽셀에 맞아떨어지지 않는다는 산수와, 그래서 캐릭터·고양이가 `LINEAR_WITH_MIPMAPS`로 그려지는가, 시트가 전부 밉맵과 함께 임포트됐는가(밉맵 없이 걸면 조용히 plain linear로 떨어진다) |

| `test_fire` | **불은 손으로 먹인다.** 코어에 도착한 것은 창고에 쌓일 뿐 타지 않는가, 몇 초가 지나도 원이 그대로인가(업그레이드가 매 프레임 다시 계산되던 시절에는 무엇이든 열을 올리면 다음 프레임에 원이 커졌다), Z를 누른 그 순간에 커지는가. 그리고 **두 번 세지 않는가** — 고양이가 나른 열석 하나가 도착할 때 한 번, 창고를 불에 넣을 때 또 한 번 세어지고 있었다. 바닥에서 줍는 것도 불을 키우지 않는다 |
| `test_rings` | 기지 사다리가 스스로를 갚는가. **단계마다 열석 광맥이 늘어나는가** — 사다리의 비용이 열석인데 한 단계가 열석을 하나도 더 주지 않으면 다음 칸이 더 멀어진다. 열석이 반경 3–6칸의 한 고리였을 때 40시드에서 반경 13·15칸이 11칸과 정확히 같은 광맥을 가졌고, 3·4단계는 15·27개를 요구하며 아무것도 돌려주지 않았다. 등급이 실제로 붙는가(그전에는 어떤 시드에서도 `보통`을 넘은 적이 없다), 구리가 **모든 시드에서** 4단계에 열리고 벨트를 지을 만큼 있는가 |
| `test_stone` | 돌. 바위밭이 좌표만으로 정해지는가(생성기가 그리는 층에서 시뮬레이션으로 옮겨 왔고, **옮긴 자리가 밭이 조용히 비는 자리다** — 그래서 개수를 센다), 광맥 위에 서지 않는가, 광맥보다 오래 걸리는가, 깬 자리가 남는가(광맥은 캐도 남고 바위는 사라진다). 그리고 **끝이 열린 벨트는 앞에 쏟는가** — 쌓이는가, 밟으면 무더기째 주워지는가, 벨트에 실린 채로도 주워지는가 |
| `test_save` | 세이브 스키마 왕복. 다른 테스트가 남긴 세이브를 물려받지 않도록 `clear_save()` 먼저 |
| `test_settings` | UI·게임 배율 저장과 복원. 그리고 **설정창이 한 목록인가** — 게임 중에는 저장·불러오기·메인화면·게임 크기·UI 크기 다섯 줄, 타이틀에서는 두 크기만. 순서를 바꿔도 값의 번호는 안 바뀌는가(UI는 여전히 0번, 게임은 1번 슬라이더다), 그리는 자리와 누르는 자리가 같은가, 다섯 줄이 화면에 들어가는가 |

## 브라우저 테스트 (사람이 부를 때)

headless는 파싱과 논리만 본다. 아래는 렌더링·입력·배포가 실제로 도는지 보는 것이고,
이름을 부르면 수행한다.

### `real test` — 표준 시나리오

**근처 수정 광맥에 채굴기 2대를 *위를 보게* 놓고, 각 채굴기에 고양이 1마리, 배치 안 한
고양이 1마리 (고양이 총 3마리).** 이 상태로 1배속으로 **3일차 밤까지** 돌린다. 1분마다
스크린샷을 찍고, 몇 분에 한 번씩 Grim에게 할 일을 시킨다.

방향이 시나리오의 일부다. 채굴기는 바라보는 칸으로 뱉으므로 나란한 광맥에 **동쪽을 보게**
놓으면 둘 다 막힌다 — 왼쪽은 오른쪽 채굴기로, 오른쪽은 세 번째 광맥으로. 위를 보게 놓으면
빈 바닥에 떨어뜨리고 유휴 고양이가 그것을 기지로 나른다. 그게 실제로 생산되는 배치다.

Grim에게 시키는 것(순환): 손 채굴 · 계기 열기 · 가챠 1연차 · 건설 목록 · 남쪽 산책 ·
화면 축소/확대. **작업 중인 고양이를 들거나 X를 누르지 않는다** — 들면 그 채굴기가 서고
X는 기계를 해체하므로, 관찰하려는 배치가 사라진다.

배치는 **`F4`(`debug_scenario`) 한 번**으로 만든다. 손으로 만들면 "왼쪽으로 1250ms 걷고
Z, 오른쪽으로 850ms 걷고 위를 보고 Z" 같은 타이밍 홀드가 열두 번이고, 한 번만 어긋나면
고양이가 채굴기가 아니라 옆 광맥 위에 선다. 그 회차는 아무것도 생산하지 않는데 그 모습이
**게임 버그와 똑같이 보인다** — 실제로 첫 파일럿이 그렇게 됐다. 검사 도구가 버그처럼
실패하는 것이 제일 나쁘다.

**`F7`(`debug_rescue`)**은 바라보는 칸에 얼어붙은 고양이를 둔다. 그 뒤는 전부 진짜다 —
절반 속도로 안고 와서 기지 2칸 안에 내려놓고 12초를 기다린다. 이 키가 있는 이유는 F4와
같다: 세계가 회차마다 새로 생성되므로 "동쪽으로 네 칸, 북쪽으로 한 칸"은 경로가 아니라
추측이고, 반 칸만 어긋나면 Z가 건설총으로 흘러가 **구조가 안 되는 게임과 똑같이 보인다.**
실제로 첫 시도에서 그렇게 됐다.

**`F8`(`debug_spill`)**은 끝이 열린 벨트 넉 줄에 자원 여섯을 실어 놓고, 기지에서 가장
가까운 바위 앞에 Grim을 세운다. 둘 다 손으로 만들기 어려운데 **잘못 만들면 아무것도
일어나지 않고, 아무것도 일어나지 않는 것이 바로 기능이 없는 모습이다.** 온기를 최대로
올리고 체온을 채우는 것도 이 키가 한다 — 첫 판은 31% 체온으로 흰 안개 속에 세웠고
스크린샷에는 벨트도 바위도 없었다. 돌 수치는 0으로 되돌린다. 이 키가 만드는 것이 둘 다
돌이라 500에서는 아무것도 안 보인다. 남는 것은 `test_debug`가 고정한다.

**`F9`(`debug_pad`)**는 터치 패드를 강제로 켠다. 패드는 `DisplayServer.is_touchscreen_available()`이 참일 때 나오는데, 터치를 흉내 낸 데스크톱 브라우저는 여전히 아니라고 답하므로 자동 검사가 패드 없는 화면을 상대하게 된다. **그리고 아무 키나 누르면 패드가 다시 숨는다** — 그것이 데스크톱 플레이어 신호이기 때문이다. 그래서 순서가 정해져 있다: 키를 먼저 전부 누르고 마지막에 F9, 그 뒤로는 터치만. CDP 터치는 캔버스에 키보드 포커스를 주지 않아서 터치 뒤의 키는 도착하지 않는다.

**`F6`(`debug_belt_loop`)**은 벨트 한 고리를 깐다 — 네 방향 직선과 네 코너, 두 회전
방향이 한 화면에 다 나온다. 벨트가 직선이냐 코너냐는 저장된 값이 아니라 **이웃**에서
나오므로, 규칙은 `test_belt_art`가 고정하고 이음매는 눈으로 본다. 깔던 자리에 광맥이
있으면 지우고 깐다 — 절반만 깔린 고리는 코너 그리기가 실패한 것과 똑같이 보인다.

확인하는 것:

- 두 채굴기가 모두 돌고 수정조각이 실제로 나오는가
- 배치된 고양이 2마리가 각자의 채굴기에 서 있는가, 작업 애니메이션이 나오는가
- 남은 1마리가 유휴 행동(바닥의 자원을 기지로 나르기)을 하는가
- 세 마리가 서로의 그림자·허기 막대를 덮지 않는가
- 허기가 떨어지면 밥통으로 가고 돌아오는가
- 밤에 셋 다 숙소로 들어가고 아침에 자기 자리로 돌아가는가
- HUD의 수정 수치가 실제 산출과 맞는가
- Grim의 행동이 배치를 방해하지 않고 각각 의도한 화면을 여는가

> **정산 카드는 `Enter`로 넘기지 않는다.** `Enter`는 `build` 액션에도 묶여 있어서 플레이
> 중에 누르면 설치를 시도한다. 카드는 화면 가운데 상자의 어두운 픽셀 비율(카드 0.96 대
> 플레이·밤·새벽 0.04 이하)로 감지하고 `Space`로 넘긴다.

### 그 밖의 브라우저 검사

| 이름 | 하는 일 |
|---|---|
| `play test` | 1배속으로 3번째 밤까지, 1분마다 스크린샷. 회차 수를 지정할 수 있다 |
| `mobile test` | 390×844 뷰포트에 실제 터치 이벤트. **`mouse.click()`은 쓰지 않는다 — 터치 레이어가 합성 마우스 이벤트를 소비한다.** 그리고 **누르고 있는 입력을 반드시 포함한다** — 아래 참고 |
| `deep test` | 랜덤 플레이가 닿지 않는 화면: 건설 목록, 계기, 가챠 10연차, 줌 양방향 한계, 설정 |
| `night test` | 밤 연출 전체를 0.7초 간격으로 촬영 |
| `perf test` | 프레임률. **같은 빌드를 3회 이상 재고 중앙값으로 판단한다** |
| `deploy test` | 배포된 URL을 열어 기대한 해시 PCK가 로드되고 캔버스에 색이 두 가지 이상 그려지는지 |

> **모바일 검사는 탭만으로 끝내지 않는다.** 채굴은 누르고 있는 동작이고, 패드가 누름만
> 보내던 시절 폰에서는 캘 수가 없었는데 **탭만 확인하는 검사로는 영원히 안 보인다.**
> `touchscreen.tap()`은 홀드를 표현할 수 없으므로 CDP로 직접 보낸다:
>
> ```js
> const cdp = await page.context().newCDPSession(page);
> const touch = (type, x, y) => cdp.send('Input.dispatchTouchEvent', {
>   type, touchPoints: type === 'touchEnd' ? [] : [{ x, y, id: 1 }] });
> await touch('touchStart', x, y); await sleep(13000); await touch('touchEnd', x, y);
> ```
>
> **"터치가 빗나갔다"와 "게임이 틀렸다"를 먼저 가른다.** 채굴 검증이 네 번 실패했는데
> 전부 조작이 엉뚱한 칸에 선 것이었고, 매번 게임이 고장난 것과 똑같이 보였다. 패드는
> 눌린 버튼을 다르게 그리므로, 두 프레임의 패드 영역을 비교해 **버튼에 불이 들어왔는지**를
> 먼저 본다. 안 들어왔으면 좌표 문제이고, 게임에 대해서는 아직 아무것도 알아낸 게 없다.

> **혼잡한 화면에서 픽셀로 재려 하지 않는다.** 고양이 여덟 마리가 있는 기지에서 게이지 아래
> 그림자를 픽셀로 찾으면 옆 고양이·드릴·기계의 어두운 부분에 붙어 편차 52px 같은 노이즈가
> 나온다. 같은 질문을 `test_crowd`가 정확히 답한다 — 화면은 그것이 이상해 *보이는지*를,
> 테스트는 그것이 실제로 어긋나는지를 본다.

브라우저 검사 준비물은 `AGENTS.md`의 "실수와 교훈"과
`~/.claude` 메모리의 browser-test-setup에 있다. 요약: Playwright를 스크래치패드에
설치하고 `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`로 띄운다.
**준비 완료 판정은 "캔버스가 있다"가 아니라 "캔버스에 색이 두 가지 이상 그려졌다"이다.**

## 이 목록에 항목을 더할 때

테스트는 **인스턴스가 아니라 결함의 종류**를 잡아야 한다. 지금까지 실제로 나온 종류:

1. 화면이 말하는 키가 다른 일을 한다 (`test_hints`)
2. 터치가 키보드와 다른 상태에 도달한다 (`test_touch`)
3. 고정한 한국어 조사가 단어와 안 맞는다 (`test_hints`)
4. 절차적 배치가 규칙적으로 반복된다 — 다양성 지표는 주기성을 못 본다 (`test_ground`)
5. 상태를 읽는 코드가 상태 기계보다 먼저 돈다 (`test_night`)
6. 셋업 헬퍼가 검사하려는 문제를 미리 해결해 준다 (`test_belt`의 주석)

**새 검사를 넣으면 고치기 전 코드에서 실패하는지 반드시 확인한다.** 양쪽에서 통과하는
검사는 아무것도 증명하지 않는다.

그리고 **왜** 통과했는지도 확인한다. `test_walk`의 중앙 검사는 두 번 공허하게 통과했다 —
한 번은 하루가 끝난 뒤에 봐서 작업 중인 고양이가 하나도 없었고, 한 번은 `place_cat`이
이미 정확히 놓아서 걸어오는 경로가 실행되지 않았다. 검사가 보려는 상황이 실행에 실제로
포함됐는지를 함께 assert한다(`worked > 1000`, `hauled_from_east`).
